# Failure matrix

Every scenario `Master-Prompt.md`'s Stage 7 lists, in the order it lists them. Most of these
mechanisms were built in earlier stages — Stage 7's job was mostly to durably recover matching-engine
state (rows 3-4) and to write this table down rather than leave the coverage implicit across a dozen
other documents.

"Data-loss possibility" means *durable* data loss — state a client was told succeeded that cannot be
recovered. A rejected or retried request is not data loss even where the table says "no": the client
simply has to try again.

| # | Failure | Impact | Detection | Immediate behavior | Recovery | Data-loss possibility | Operational alert |
|---|---|---|---|---|---|---|---|
| 1 | Kafka unavailable | Execution/position events stop propagating downstream; matching and order admission unaffected | Producer send failures; consumer lag stalls | `BufferedKafkaEventPublisher` buffers in a bounded in-process queue, non-blocking — a matching worker never waits on Kafka | Publisher resumes automatically once the broker returns; buffered events drain | **Yes**, if the outage outlasts the buffer: events are dropped and counted, no local durable record of what was dropped (unchanged Stage 4 limitation) | `trading.events.dropped` > 0; consumer lag flat. [Kafka design](kafka-design.md); `KafkaOutageIntegrationTest` |
| 2 | PostgreSQL unavailable | Portfolio consumer (`PortfolioProcessor`) can't write positions/executions | `TransientPersistenceException` from `PortfolioRepository` | Consumer retries on a fixed, unlimited backoff — deliberately never dead-lettered (ADR-009) — blocking only its own partition | Automatic once Postgres returns; offset was never committed, so nothing is skipped | No — record redelivered until it succeeds | Consumer lag rising unboundedly for `position-processor`, DLQ depth staying at zero. `DatabaseOutageIntegrationTest` |
| 3 | Gateway restart | In-memory order registry, idempotency map, rate-limit buckets and risk snapshot all reset | N/A — planned or crash | Matching book: recovered via journal replay (ADR-015) before the router accepts traffic. Risk positions: rebuilt by replaying the executions topic; gateway reports out of service until caught up (`ReplayReadiness`) | Matching and risk: automatic, see Recovery column. Gateway idempotency/rate-limit state: **not durable**, and its order-id allocator (`OrderRegistry`) restarts from 1 | Matching/risk: no. Gateway idempotency: **yes** — and sharper than a narrow race window: since the matching engine now recovers its book but the gateway's order-id counter does not, **the very first order after a restart with any recovered resting orders is guaranteed to collide** (`DUPLICATE_ORDER_ID`), observed directly against a real running gateway, not hypothesized | `/actuator/health` readiness; `ReplayReadiness` log lines; a `DUPLICATE_ORDER_ID` rejection immediately after restart is itself the symptom. `MatchingRestartIntegrationTest` |
| 4 | Matching-worker restart / process loss | Without Stage 7: total loss of that worker's book. With it: fully recovered | Process exit / supervisor restart | `OrderRouter` replays each worker's journal synchronously before starting any worker | Byte-for-byte identical resting book, order statuses and execution-id continuity — proven, not assumed | Only a command still in the in-memory queue at crash time, which was never acknowledged to its caller anyway — an ordinary retry, not lost data | None automated yet; the journal directory's growth is unmonitored (ADR-015). `OrderRouterRecoveryTest`, `MatchingRestartIntegrationTest` |
| 5 | Portfolio consumer crash | A `position-processor` group member dies mid-processing | Kafka group-coordinator rebalance | Partition reassigned to a surviving member; a trade caught mid-transaction is either fully committed or fully rolled back, never half-applied (ADR-010) | Automatic; resumes from last committed offset | No | Rebalance events on the client. `PipelineFailureIntegrationTest.aRebalanceNeitherLosesNorDuplicatesExecutions` |
| 6 | Network interruption | Indistinguishable at the application layer from rows 1/2 — a broker or database that cannot be reached looks the same whether the process died or the network did | Same as rows 1/2: connection refused/timeout | Same as rows 1/2 | Same as rows 1/2 | Same as rows 1/2 | Same as rows 1/2. `KafkaOutageIntegrationTest`, `DatabaseOutageIntegrationTest` pause the container, which is the client-observable equivalent of a partition |
| 7 | Duplicate execution | None, if handled — an execution redelivered by Kafka or regenerated by journal replay must not double-book a position | N/A — expected, not exceptional | `execution_id` primary key / `ON CONFLICT DO NOTHING` makes a duplicate insert a no-op (ADR-010); risk engine and audit log dedupe by event id the same way | N/A — never incorrect to begin with | No | `trading.consumer.duplicates` (informational; nonzero is normal). `PortfolioUpdaterTest`, `ExecutionPipelineIntegrationTest` |
| 8 | Duplicate order submission | A client retries the same `clientOrderId` after a timeout or its own crash | Gateway idempotency registration keyed on `(account, clientOrderId)` | `OrderIngressService` returns the original response marked `duplicate: true` rather than routing a second command | N/A | **Yes**, narrowly — the registry is in-memory; see row 3's gateway-restart caveat | None dedicated. ADR-004 |
| 9 | Out-of-order messages | Kafka could in principle reorder records across partitions during redelivery/rebalance; never within one partition, by design | N/A | Every consumer relies only on per-partition (per-symbol) order — nothing here needs cross-partition order | N/A | No | None needed. ADR-007; market data has the analogous concern on its own independent feed, handled separately (ADR-012) |
| 10 | Queue saturation | A matching worker's bounded admission queue is full | `ArrayBlockingQueue.offer` returns false | `OrderRoutingRejectedException(QUEUE_FULL)` thrown immediately at admission — the caller learns now, not after a timeout | Caller retries; queue drains as the worker catches up | No — the command was never accepted | `WorkerMetricsSnapshot.saturatedCommands()`. `OrderRouterTest.fullQueueRejectsImmediatelyAndDoesNotReserveIdentifiers` |
| 11 | Slow consumer | A Kafka consumer group or a market-data WebSocket subscriber falls behind | Consumer lag; per-subscriber drop count | Kafka: backlog grows on that partition only, other groups unaffected. Market data: the slow subscriber's own bounded queue drops its oldest update, never blocks the feed or another subscriber (ADR-013) | Kafka: works through the backlog once no longer slow. Market data: catches up, or is disconnected after sustained overflow | Kafka: no, the topic retains everything. Market data: **yes**, by design — current state matters more than history for a live feed | `kafka.consumer.fetch.manager.records.lag.max`; `trading.marketdata.subscribers` (per-subscription drop counts not yet a registered metric — see market-data.md). `PipelineFailureIntegrationTest.aBacklogIsWorkedThroughRatherThanDropped`, `MarketDataHubTest` |
| 12 | Poison Kafka event | One malformed or semantically-impossible record could stop a partition forever under naive infinite retry | `DeserializationException` / `InvalidEventException` | Dead-lettered on the **first** attempt, no retry budget spent — the one case in this table that deliberately does not retry (ADR-009) | Partition keeps moving; the record sits on the `.dlq` topic until an operator looks — nothing consumes it yet (Stage 8) | **Yes, functionally** — a dead-lettered execution leaves the portfolio short that trade until `PositionReconciliation` is run and the gap investigated | `trading.consumer.dead.lettered`. `PipelineFailureIntegrationTest.anUnparseableRecordIsDeadLetteredAndDoesNotBlockThePartition`, `.aStructurallyValidButImpossibleRecordIsDeadLettered` |
| 13 | Partial downstream outage | One consumer group's own dependency fails while the others keep working | Per-group processing errors/metrics — each group is independent | `execution-processor`, `position-processor`, `audit-processor` and `risk-state-updater` are four independent subscribers to the same topics; one blocked on its dependency never holds up another | Same as that dependency's own row (1 or 2) | Same as that dependency's own row | Same as that dependency's own row. [Kafka design](kafka-design.md)'s consumer table |
| 14 | Traffic burst | A sudden spike in order or market-data volume | Rate-limiter rejection rate; queue depth rising | Gateway's per-account token bucket sheds excess (`429`, `Retry-After`); matching queues absorb up to capacity then reject (row 10); market-data subscribers absorb up to their own queue then drop-oldest (row 11) | Automatic once the burst subsides | No new possibility beyond rows 10/11's own answers | `RateLimitExceededException` rate; queue-depth metrics. `RateLimitApiTest`; `ConcurrentOrderFlowSimulator` exercises the shape of this without being presented as a benchmark |
| 15 | Publish send failure | One event's `send()` call itself is NACKed or times out — the broker is otherwise reachable and healthy, unlike row 1's outage | `KafkaTemplate.send()`'s returned future completes exceptionally | `BufferedKafkaEventPublisher`'s dispatcher logs it and increments a counter; the event is not requeued or retried | None — there is no retry or dead-letter path for this specific failure today | **Yes, unconditionally** — every occurrence is a lost event, not just a possibility past some threshold like row 1's buffer | `trading.events.publish.failed` > 0. No integration test forces a real per-send NACK (would need a broker-side fault injection this stack does not have); found and disclosed during a Stage 9 verification pass, not exercised by a dedicated test |
