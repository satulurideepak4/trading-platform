# Networking comparison: HTTP+JSON vs. HTTP+Protobuf vs. TCP+binary

Stage 9's own docs (`docs/performance-engineering.md`, "What this stage did not attempt") named
two open questions and deferred them here by name: JSON vs. Protobuf, and REST vs. a persistent
connection. This document answers both with real, measured numbers — no figure below was
estimated, extrapolated, or written before the run that produced it. Full hardware disclosure and
reproduction commands: `docs/benchmark-methodology.md`. Wire format for the TCP path:
`docs/tcp-protocol.md`. Design rationale: `docs/architecture-decisions/ADR-016-low-latency-tcp-protocol.md`.

**Bottom line, stated up front because the master prompt is explicit that it must not be assumed:**
on this hardware, at these load levels, the persistent TCP+binary path is faster than both REST
paths on every metric measured — but the fastest *serialization* format measured is Protobuf, not
the hand-rolled TCP binary codec. TCP wins on connection/framing economics, not because binary
encoding automatically beats everything else. Both halves of that sentence are load-bearing; see
"Serialization overhead" below for the number that would make a purely encoding-focused conclusion
wrong.

## What was measured

Six `LoadTestRunner` runs — three transports × two load regimes — each against a freshly reset
`docker compose` stack (`down -v && up -d --build`) so no run's resting orders or open-order count
bled into the next one's results, plus one JMH suite isolating pure serialization cost. Every
report referenced below lives in `benchmarks/results/`, generated by `ReportWriter`, unedited.

* **Typical load** — `--orders=150 --producers=4`: comfortably under the gateway's fixed 2-second
  `trading.matching.command-timeout`, a clean apples-to-apples number for each transport.
* **Burst load** — `--orders=400 --producers=8`: 8 producer threads submitting as fast as the
  workload's pacing allows (`steady`'s 50,000/s target is not the binding constraint at this
  scale) — same workload, same random seed, more concurrent pressure on the one thing every
  transport shares: the unchanged matching-engine pipeline downstream of it.

## Results

### Typical load (150 orders, 4 producers)

| Transport | Throughput (orders/s) | p50 (ms) | p95 (ms) | p99 (ms) | Rejected |
|---|---|---|---|---|---|
| TCP + binary | **528.9** | **120.0** | **256.9** | **262.6** | 0/150 |
| HTTP + Protobuf | 222.8 | 464.4 | 562.6 | 584.1 | 0/150 |
| HTTP + JSON | 114.9 | 806.4 | 1158.5 | 1217.3 | 0/150 |

Reports: `steady-tcp-binary-typical-20260820-044815921.md`,
`steady-rest-protobuf-typical-20260820-044921279.md`,
`steady-rest-json-typical-20260820-044842069.md`.

### Burst load (400 orders, 8 producers)

| Transport | Throughput (orders/s) | p50 (ms) | p95 (ms) | p99 (ms) | Rejected |
|---|---|---|---|---|---|
| TCP + binary | **478.5** | **305.7** | **767.4** | **785.1** | 0/400 |
| HTTP + Protobuf | 190.7 | 1001.7 | 1862.1 | 1945.8 | 0/400 |
| HTTP + JSON | 180.0 | 1415.7 | 2023.3 | 2074.3 | 0/400 |

Reports: `steady-tcp-binary-burst-20260820-045000834.md`,
`steady-rest-protobuf-burst-20260820-045112173.md`,
`steady-rest-json-burst-20260820-045027541.md`.

The ranking is identical in both regimes — TCP fastest, Protobuf second, JSON slowest, on both
throughput and every latency percentile — which is a more trustworthy result than either run alone:
it is not one lucky sample, and the gap does not close as load increases within the range tested.

**These are absolute wall-clock numbers on a shared developer laptop** (Apple M1 Pro, 8 cores,
16GB RAM, one layer of Docker Desktop virtualization for `trading-gateway`, everything else — Kafka,
Postgres, Prometheus, Grafana — running concurrently in the same Docker network) — not
vendor-comparable throughput claims. What is trustworthy is the *relative* comparison: all three
transports were measured back to back, in the same session, against the same code, same workload,
same seed, same freshly-reset gateway state.

## Why TCP wins here

**Connection establishment cost is paid once, not per order.** Every `rest-json`/`rest-protobuf`
submission is a fresh HTTP/1.1 request-response exchange (`java.net.http.HttpClient`'s connection
pool reuses TCP connections across requests where it can, but still pays HTTP request/response
framing — headers, a fresh servlet-thread dispatch — every time). `tcp-binary` connects and
authenticates exactly once per `LoadTestRunner` process, then pipelines every subsequent
submit/cancel/replace over that one already-open, already-authenticated connection. At 150-400
orders this is the single largest structural difference between the three paths, and it shows: TCP
wins even at typical load, where nothing is near saturating the shared matching pipeline.

**Framing overhead is smaller and fixed-cost.** A `SUBMIT` frame is a handful of longs, two short
strings, and a 4-byte length prefix — no header parsing, no per-request MIME negotiation. See
`docs/tcp-protocol.md` for the exact byte layout.

**Backpressure is structurally different, and directly observable in what was actually measured.**
`SubmissionTarget.queueDepth()` means something different per transport, and the burst-load reports
show it plainly: `tcp-binary`'s report shows `queueDepth max=399 avg=169.7` — the number of
requests sent on the one shared connection whose `ACK` hasn't arrived yet, a real, bounded,
in-process count. Both REST targets report `queueDepth=0` always, because an HTTP client has no
equivalent concept — each request is its own independent exchange with nothing shared to measure a
depth on (see `RestJsonSubmissionTarget.queueDepth()`'s own Javadoc). This is not TCP being "worse
at admitting work" — it's the one transport of the three whose backpressure is visible to its own
client at all, because a persistent connection has client-side state to report on and a
connection-per-request model does not.

## Serialization overhead: measured separately, and the result that keeps this honest

`SerializationBenchmark` (JMH, 2 forks, 5×1s warmup, 5×1s measurement — this repository's standard
discipline, see `docs/benchmark-methodology.md`) isolates *only* encode/decode cost for one
representative `SUBMIT`-equivalent message, no network, no matching engine:

| Format | Encode (ops/µs) | Decode (ops/µs) | Encode (µs/op, sample mean) | Decode (µs/op, sample mean) |
|---|---|---|---|---|
| Protobuf | **22.820 ± 1.718** | **13.771 ± 2.118** | **0.081 ± 0.013** | **0.131 ± 0.024** |
| Hand-rolled binary (`OrderEntryCodec`) | 6.045 ± 0.503 | 5.793 ± 2.768 | 0.314 ± 0.030 | 0.195 ± 0.021 |
| JSON (Jackson) | 4.105 ± 0.376 | 2.303 ± 0.634 | 0.275 ± 0.015 | 0.502 ± 0.067 |

Full results: `benchmarks/results/jmh-serialization-results.json`.

**Protobuf's generated, code-specialized serializer is faster to encode and decode than this
project's own hand-rolled TCP binary codec** — by roughly 3-4×. `OrderEntryCodec` is not
hand-tuned for raw serialization speed; it prioritizes an explicit, auditable, protocol-owned wire
format (see ADR-016's discussion of the `Side`/`OrderType` ordinal bug it exists to avoid
repeating) over allocation-minimizing tricks a generated serializer gets for free. JSON is slowest
at both, consistent with Jackson's reflection-based (de)serialization having more inherent work per
field than either binary format.

**This is precisely why TCP's end-to-end win above is not "because binary serialization is
faster."** If serialization cost were what dominated end-to-end latency, `rest-protobuf` — using
the *fastest* serializer measured — would beat `tcp-binary`, using a slower one. It does not, in
either load regime. TCP's advantage comes from what's described above (connection reuse, framing,
pipelining), and Protobuf's real, measured serialization advantage over JSON is *also* real and
visible in the REST-vs-REST comparison (`rest-protobuf` beats `rest-json` on every metric, at both
load levels) — the two effects are independent and both genuine, not the same effect double-counted.

## Kernel networking overhead, buffering, and the mechanisms behind these numbers

* **`TCP_NODELAY` was set explicitly** on both the server (`TcpConnection`) and the benchmark
  client, on both `tcp-binary` and — via the JDK's own `HttpClient` internals — is not directly
  controllable for the REST targets. Left at the JDK/kernel default, Nagle's algorithm can hold a
  small write (most of what this protocol sends: an ACK is a few dozen bytes) for tens of
  milliseconds waiting to coalesce with more outbound data that may never come. This was named as a
  specific risk during this stage's design review, precisely because leaving it at the default
  would have silently decided the outcome of this exact measurement.
* **Partial reads/writes are real, not theoretical**, because TCP delivers a byte stream, not a
  message stream — the kernel is free to split a logical write across multiple deliveries to the
  receiving application, and a receiver that assumes one `read()` call returns one whole frame will
  eventually corrupt its own framing under real network conditions. `FrameIOTest` proves
  `OrderEntryCodec`'s framing survives this directly, using a fragmenting test `InputStream` that
  hands back as little as 1–3 bytes per call; production code exclusively uses
  `DataInputStream.readFully`, never a bare `read()`, for exactly this reason.
* **Buffering**: each `TcpConnection` owns a small bounded outbound queue plus a dedicated writer
  thread (mirroring `QueuedMarketDataSubscription`/ADR-013's existing drop-oldest,
  disconnect-after-sustained-overflow pattern) so a slow reader cannot block the matching pipeline
  that produced its fill; REST has no equivalent concept because there is no persistent connection
  to buffer on — the underlying servlet response either writes or the request fails.
* **Framing**: see `docs/tcp-protocol.md` in full; summarized above under "Framing overhead."

## A caveat from real production-like behavior, not part of the controlled comparison above

During earlier, non-isolated exploratory runs in this same session — multiple `LoadTestRunner`
invocations fired back to back against one long-lived gateway, deliberately *not* reset between
them, closer to how a real always-on venue connection would actually be used — the REST/JSON path
was observed to produce real `MatchingTimeoutException`s (`event=matching_timeout`, the gateway's
own 2-second `trading.matching.command-timeout` genuinely exceeded) under a burst of concurrent
requests once enough resting orders had accumulated on the account from prior runs, while the same
nominal order count against `tcp-binary` did not. That observation is **not** reproduced in the
controlled, freshly-reset comparison above (all six controlled runs completed with zero rejections
and zero timeouts), so it is reported here separately rather than folded into the headline numbers:
the isolated experiment is the trustworthy one for comparing transports fairly, but the
uncontrolled one is a real, plausible signal worth naming rather than discarding — REST's
connection-per-request model has no equivalent to `tcp-binary`'s single shared connection (bounded
by `trading.tcp.dispatch-pool-size`, 8 by default) naturally capping how many requests one client
can have simultaneously in flight against the shared matching pipeline; a REST client with enough
concurrent HTTP connections has no such structural limit until Tomcat's own thread pool is
exhausted. This asymmetry is a genuine, structural difference between the two connection models
worth further, deliberately-designed measurement in a future stage — it should not be read as
either confirmed or refuted by the single accumulated-state observation that surfaced it.

## Conclusion

* TCP+binary is faster than both REST paths on every measured metric, at both load levels tested,
  on this hardware. This is a real, repeatable, structural result of connection reuse and
  pipelining — not an assumption, and not solely a consequence of binary encoding.
* Protobuf beats JSON on every measured metric, both in pure serialization (JMH) and end-to-end
  over REST (`LoadTestRunner`) — a real, repeatable win with no caveat found during this stage's
  testing.
* Protobuf's serializer is faster than this project's own hand-rolled TCP binary codec at raw
  encode/decode — a result that would be easy to omit because it complicates the headline "TCP
  wins" story, and is reported here in full specifically because omitting it would violate the
  master prompt's explicit instruction not to claim more than what was measured.
* REST remains the right default for anything that isn't specifically latency-sensitive: any HTTP
  client can talk to it, no protocol library needed, and both REST paths here still completed every
  request correctly at both load levels. The persistent TCP protocol is what this stage set out to
  build as an experiment alongside REST, not a case for replacing it — see ADR-016's own framing.
